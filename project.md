## 1. Что это за проект в двух словах

Представь бумажные карточки для зубрёжки: с одной стороны вопрос, переворачиваешь — ответ. Твой проект — это те же карточки, только:

- живут не в коробке, а в браузере;
- хранятся не у тебя на столе, а на маленьком «сервере» (`json-server`), который прикидывается настоящим бэкендом;
- можно искать, сортировать, листать по страницам, отмечать «выучено», добавлять новые и редактировать старые.

React в этой аналогии — это не карточки и не сервер. React — это **человек, который перекладывает карточки на столе** каждый раз, когда что-то меняется (ты нажал кнопку, пришли данные с сервера) — и делает это быстро, без твоего участия, сам решая, какие карточки перерисовать, а какие оставить как есть.

## 2. Как устроен весь путь данных (общая карта)

Прежде чем нырять в детали, посмотри на маршрут целиком. Вот что происходит, когда ты открываешь сайт:

```
main.jsx                     — точка входа, "включаем свет"
  └─ App.jsx                 — говорит: "какой адрес в браузере — такую страницу и показывай"
       └─ MainLayout.jsx     — общая рамка сайта: шапка + подвал + место под страницу
            └─ HomePage.jsx (или другая страница) — начинает "стучаться" на сервер
                 └─ useFetch (хук)         — сходил на json-server, подождал, вернул данные
                      └─ setState(...)     — "запомни эти данные"
                           └─ React перерисовывает экран новыми данными
```

Файлы, которые за это отвечают:

- `src/main.jsx` — запускает React и вставляет его в `<div id="root">` из `index.html`.
- `src/App.jsx` — таблица маршрутов ("роутов"): какому адресу (URL) какая страница соответствует.
- `src/components/MainLayout/MainLayout.jsx` — общий каркас (шапка, подвал), внутри которого меняются только страницы.
- `src/constants/index.js` — тут единственная строчка `API_URL`, адрес твоего фейкового сервера.
- `src/db.json` — "база данных" в виде обычного JSON-файла, которую читает `json-server`.

**Аналогия:** `App.jsx` — это как ресепшн в отеле: ты называешь номер комнаты (URL), тебя направляют в нужную дверь (страницу). `MainLayout` — это сам отель со стенами и крышей, они не меняются, меняется только то, что происходит в конкретной комнате.

## 3. Кирпичики по концепциям

Дальше — по одной концепции за раз. Формат каждой: **что это → зачем → где у тебя → аналогия → как перенести в другой проект**.

### 3.1 Компоненты и props

**Что это.** Компонент — это функция, которая возвращает разметку (JSX). Props — это аргументы, которые ты ей передаёшь, как параметры в обычную функцию.

**Где у тебя.** Смотри `src/components/Button/Button.jsx`:

```jsx
export const Button = (props) => {
  return (
    <button
      className={`${cls.btn} ${props.isActive ? cls.active : ""}`}
      onClick={props.onClick} disabled={props.isDisable}
    >
      {props.children}
    </button>
  );
};
```

Это универсальная кнопка. Она сама не знает, что делать по клику — это решает тот, кто её вызывает. Пример вызова — `src/components/QuestionCard/QuestionCard.jsx:26`:

```jsx
<Button onClick={() => navigate(`/questions/${card.id}`)}>Answer</Button>
```

**Аналогия.** Компонент — это форма для выпечки печенья. Props — это начинка, которую ты кладёшь каждый раз новую, а форма (разметка, стили, поведение) — одна и та же.

**Как переносить.** В любом React-проекте: если один и тот же кусок разметки повторяется 2+ раза с небольшими отличиями — выноси в компонент, а отличия делай props.

### 3.2 JSX и рендер списков (`.map`, `key`)

**Что это.** JSX — это HTML прямо внутри JavaScript. Чтобы вывести список карточек, ты не пишешь цикл `for`, а используешь `.map()`, потому что JSX — это просто данные (массив элементов), и `.map()` как раз превращает массив данных в массив JSX-элементов.

**Где у тебя.** `src/components/QuestionCardList/QuestionCardList.jsx`:

```jsx
{cards.map((card, index) => {
  return <QuestionCard card={card} key={index} />;
})}
```

**Про `key`.** React использует `key`, чтобы понять "это та же карточка, что была, или новая?" между перерисовками. Сейчас у тебя `key={index}` (0, 1, 2...) — это работает, но не идеально: если карточки в массиве переставятся местами (например, после сортировки), React решит, что это "новые" карточки на старых местах, и может напутать состояние компонентов или лишний раз всё перерисовать. Правильнее — `key={card.id}`, потому что `id` уникален и не меняется при пересортировке. **Это попадёт в роадмап ниже как мини-задание.**

**Аналогия.** `key` — это бирка с именем на карточке. Без бирки React ориентируется только по порядку в очереди — а если очередь перемешать, он перепутает, кто есть кто.

### 3.3 Роутинг (react-router-dom)

**Что это.** Роутинг — это связь между адресом в адресной строке браузера и тем, какой компонент показать.

**Где у тебя.** `src/App.jsx`:

```jsx
<BrowserRouter>
  <Routes>
    <Route element={<MainLayout />}>
      <Route path="/" element={<HomePage />} />
      <Route path="/addquestion" element={<AddQuestionPageLazy />} />
      <Route path="/questions/:id" element={<QuestionPage />} />
      <Route path="/editquestion/:id" element={<EditQuestionPage />} />
      <Route path="*" element={<NotFoundPage />} />
    </Route>
  </Routes>
</BrowserRouter>
```

- `:id` — это **параметр маршрута**. Адрес `/questions/5` означает "покажи QuestionPage и дай ей знать, что id = 5". Внутри страницы это читается хуком `useParams()` — смотри `src/components/pages/QuestionPage/QuestionPage.jsx:13`: `const { id } = useParams();`.
- `<Route element={<MainLayout />}>` с вложенными `<Route>` внутри — это "родительский" маршрут. `MainLayout` рисует рамку (шапку/подвал), а куда именно вставить конкретную страницу, решает `<Outlet />` внутри него (`src/components/MainLayout/MainLayout.jsx:18`). Это называется **вложенный роутинг**.
- `*` — маршрут-ловушка на все остальные адреса (страница 404).
- `useNavigate()` — хук, чтобы переходить на другой адрес программно (по клику), а не по ссылке. Пример — `src/components/QuestionCard/QuestionCard.jsx:6,26`.

**Аналогия.** `BrowserRouter` — это диспетчер такси, который смотрит на адрес назначения и решает, какую машину (компонент) отправить. `:id` — это уточнение адреса ("дом 5", а не просто "улица").

**Как переносить.** Этот паттерн (layout-роут + вложенные страницы + `:id` + `useParams`) — стандарт почти для любого React-приложения с несколькими страницами и "карточками с деталями" (товары, посты, профили и т.д.).

### 3.4 Состояние: `useState` и `useEffect`

**Что это.** `useState` — это "память" компонента: значение, которое живёт между перерисовками и при изменении вызывает перерисовку. `useEffect` — это способ сказать React "после того как отрисуешь компонент, сделай ещё вот это" (обычно — что-то, что не связано напрямую с рендером: запрос на сервер, подписка, таймер).

**Где у тебя.** `src/components/pages/QuestionPage/QuestionPage.jsx`:

```jsx
const [card, setCard] = useState(null);
...
useEffect(() => {
  fetchCard();
}, []);
```

Разбор:
- `useState(null)` — сначала карточки нет, `card === null`.
- `useEffect(..., [])` — пустой массив зависимостей `[]` означает "выполни этот код один раз, сразу после первого рендера" (аналог `componentDidMount` из старого React). Здесь это "как только страница открылась — сходи за данными".
- Когда `fetchCard()` получит данные, он вызовет `setCard(data)`, значение изменится → React перерисует компонент → теперь `card !== null` → на экране появится содержимое карточки.

Ещё один пример синхронизации состояний друг с другом — `src/components/pages/QuestionPage/QuestionPage.jsx:45-47`:

```jsx
useEffect(() => {
  card !== null && setIsChecked(card.completed);
}, [card]);
```

Тут зависимость — `[card]`: эффект выполнится заново каждый раз, когда `card` изменится (не только при монтировании).

**Правило, которое стоит запомнить:** *эффект — это точка синхронизации компонента с чем-то внешним* (сервер, DOM, таймер, подписка). Если можно вычислить значение прямо во время рендера — не нужен `useEffect`, это лишнее звено. Про это — в разделе 3.7 про `useMemo`.

**Аналогия.** `useState` — это листок с заметкой на холодильнике, который React перечитывает при каждой перерисовке. `useEffect` — это будильник "как только зайдёшь на кухню (компонент отрисовался) — включи чайник (сделай запрос)".

### 3.5 Кастомный хук `useFetch`

**Что это.** Хук — это просто функция, начинающаяся с `use`, которая может пользоваться другими хуками (`useState` и т.д.) внутри себя. Кастомный хук — тот, который написал ты сам, чтобы не повторять один и тот же код в разных местах.

**Где у тебя.** `src/hooks/useFetch.js`:

```js
export const useFetch = (callback) => {
  const [isLoader, setIsLoader] = useState(false);
  const [error, setError] = useState("");

  const fetchFn = async (arg) => {
    try {
      setIsLoader(true);
      setError("");
      await delayFn();
      const response = await callback(arg);
      return response;
    } catch (error) {
      setError(error.message);
      toast.error(error.message);
    } finally {
      setIsLoader(false);
    }
  };
  return [fetchFn, isLoader, error];
};
```

Что он прячет "под капотом", чтобы тебе не писать это заново в каждой странице:
1. Включить индикатор загрузки перед запросом, выключить после — неважно, успех или ошибка (`finally`).
2. Если что-то упало — сохранить текст ошибки и показать всплывающее уведомление (`toast`).
3. Искусственная задержка `delayFn()` — просто чтобы во время учёбы было видно лоадер (в реальном проекте это не нужно, реальные запросы и так не мгновенные).

Использование — `src/components/pages/QuestionPage/QuestionPage.jsx:21-30`:

```jsx
const [fetchCard, isCardLoading] = useFetch(async () => {
  const response = await fetch(`${API_URL}/react/${id}`);
  if (!response.ok) throw new Error("Card not found");
  const data = await response.json();
  setCard(data);
});
```

Ты передаёшь **свою** логику запроса (`callback`), а `useFetch` вокруг неё оборачивает лоадер/ошибки/задержку. Это называется **паттерн "функция высшего порядка"** — хук принимает функцию и возвращает новую функцию с добавленным поведением.

**Аналогия.** Это как чехол для телефона: сам телефон (твой запрос к серверу) не меняется, но чехол (`useFetch`) добавляет вокруг него защиту (обработку ошибок) и лампочку (индикатор загрузки).

**Как переносить.** Такой хук — один из самых полезных паттернов, которые стоит уносить с собой в любой проект: любая логика "запрос + лоадер + ошибка" достойна такой обёртки, чтобы не копипастить `try/catch/finally` по всем компонентам.

### 3.6 Формы в React 19: `useActionState` + `action`

Это самая "свежая" часть твоего проекта — React 19 добавил новый способ работать с формами, без `onSubmit` и `preventDefault()`, к которому ты, возможно, привык по туториалам.

**Где у тебя.** `src/components/pages/AddQuestionPage/AddQuestionPage.jsx`:

```jsx
const createCardAction = async (_prevState, formData) => {
  try {
    await delayFn();
    const newQuestion = Object.fromEntries(formData);
    // ...
    const response = await fetch(`${API_URL}/react`, {
      method: "POST",
      body: JSON.stringify({ ... }),
    });
    if (!response.ok) throw new Error(response.statusText);
    const question = response.json();
    toast.success("Card created successfully");
    return isClearForm ? {} : question;
  } catch (error) {
    toast.error(error.message);
    return {};
  }
};

const AddQuestionPage = () => {
  const [formState, formAction, isPending] = useActionState(createCardAction, {
    clearForm: true,
  });
  return (
    <QuestionForm formAction={formAction} state={formState} isPending={isPending} .../>
  );
};
```

Разбор по шагам:
1. `useActionState(fn, initialState)` возвращает три вещи: `[состояние, экшен-функция для передачи в форму, флаг "идёт ли отправка"]`.
2. `createCardAction` — это твоя функция-обработчик. Она получает `(предыдущее_состояние, formData)`. `formData` — это специальный объект браузера `FormData`, который автоматически собирает **все** значения из полей формы по их `name` (посмотри `src/components/QuestionForm/QuestionForm.jsx` — у каждого `<textarea name="question">` и т.д.).
3. `Object.fromEntries(formData)` превращает `FormData` в обычный `{question: "...", answer: "...", ...}`.
4. Значение, которое `createCardAction` вернёт (`return isClearForm ? {} : question`) — становится новым `formState`. Это и есть "состояние" из `useActionState`, которое ты передаёшь обратно в `<QuestionForm state={formState} />`, чтобы, например, показать только что созданный вопрос в форме или, наоборот, очистить поля.
5. В самой форме (`<form action={formAction}>`) не нужен `onSubmit`/`preventDefault` — React сам перехватывает отправку формы и вызывает твой экшен.
6. `isPending` — автоматический флаг "запрос ещё выполняется", чтобы, например, задизейблить кнопку (`<Button isDisable={isPending}>`).

**Незаполненные поля через `defaultValue`.** В `src/components/QuestionForm/QuestionForm.jsx` поля используют `defaultValue={state.question}`, а не `value={state.question}`. Это **неконтролируемые** поля: React один раз подставляет значение, а дальше пользователь печатает сам, без промежуточных `onChange` на каждую букву. Для форм, где не нужна проверка "на лету" при каждом нажатии клавиши, это проще и производительнее контролируемых полей (`value` + `onChange`).

**Твоя незавершённая часть.** В `src/components/pages/EditQuestionPage/EditQuestion.jsx:7`:

```jsx
const [formState, formAction, isPending] = useActionState(() => {}, {
  ...initialState,
  clearForm: false,
});
```

Экшен здесь — пустая функция `() => {}`. Форма редактирования отрисовывается и заполняется старыми данными (`initialState`), но **при отправке ничего не происходит** — нет ни `fetch` с `PATCH`/`PUT`, ни `toast`, ни возврата на страницу вопроса. Это точная копия структуры `createCardAction`, только с другим HTTP-методом и URL. **Это твоё первое практическое задание в роадмапе ниже.**

**Аналогия.** `useActionState` — это как автомат с газировкой: ты нажимаешь кнопку (отправляешь форму), автомат сам знает, что нужно "подождать, пока нальётся" (`isPending`), а на экране автомата остаётся последнее сообщение ("спасибо" или "ошибка" — это и есть `formState`), которое видно, пока не нажмёшь кнопку снова.

**Как переносить.** Этот паттерн (`useActionState` + `<form action={fn}>`) — новый стандартный способ обрабатывать формы в React 19+, без ручного `onSubmit`/`preventDefault`/локального `useState` под каждое поле.

### 3.7 `useMemo`, `useRef`, `useId`, `memo` — точечные оптимизации

Эти четыре штуки не связаны друг с другом напрямую, но у тебя все они встречаются рядом, так что разберём вместе.

**`useMemo` — "запомни результат вычисления, пока не изменились зависимости".**
`src/components/pages/HomePage/HomePage.jsx:49-60`:

```jsx
const cards = useMemo(() => {
  if (questions?.data) {
    if (searchValue.trim()) {
      return questions.data.filter((d) =>
        d.question.toLowerCase().includes(searchValue.trim().toLowerCase()),
      );
    }
    return questions.data;
  }
  return [];
}, [questions, searchValue]);
```

Без `useMemo` фильтрация массива запускалась бы **при каждой** перерисовке компонента (а их может быть много — например, из-за не связанного с поиском изменения другого стейта). `useMemo` пересчитывает `cards` только тогда, когда изменились `questions` или `searchValue` — именно то, от чего реально зависит результат. Это и есть разница с `useEffect` из раздела 3.4: тут не нужно ничего "синхронизировать с внешним миром", результат целиком вычисляется из данных, которые уже есть — поэтому `useMemo`, а не `useEffect` + ещё один `useState`.

**`useRef` — "ссылка на что-то, что не должно вызывать перерисовку при изменении".**
`src/components/pages/HomePage/HomePage.jsx:21` + `92`:

```jsx
const controlsContainerRef = useRef();
...
controlsContainerRef.current.scrollIntoView({ behavior: "smooth" });
```

Тут `ref` привязан к DOM-элементу (`<div ref={controlsContainerRef}>`), чтобы потом напрямую позвать браузерный метод `scrollIntoView` — то, что React не делает сам через пропсы/состояние.

**`useId` — генератор уникального id, безопасного для связки `<label htmlFor>` / `<input id>`.**
`src/components/pages/QuestionPage/QuestionPage.jsx:11`:

```jsx
const checkboxId = useId();
...
<label htmlFor={checkboxId}>...
<input id={checkboxId} .../>
```

Если бы ты просто написал `id="checkbox"` и на странице было бы два таких компонента одновременно — оба чекбокса получили бы одинаковый `id`, что ломает доступность (клик по label одного затрагивал бы оба). `useId` гарантирует уникальность на каждый рендер компонента.

**`memo` — "не перерисовывай этот компонент, если пропсы не изменились".**
`src/components/QuestionCardList/QuestionCardList.jsx:4`:

```jsx
export const QuestionCardList = memo(({ cards }) => { ... });
```

Если родитель (`HomePage`) перерисовался из-за изменения, скажем, `sortSelectValue`, но массив `cards` остался тем же самым (по ссылке) — `memo` не даст `QuestionCardList` перерисоваться зря.

**Аналогия для всех четырёх:** `useMemo` — калькулятор, который не пересчитывает заново, если ты не поменял цифры. `useRef` — стикер с адресом, который ты можешь достать напрямую, не спрашивая у React разрешения. `useId` — как индивидуальный номер бейджа на конференции, чтобы не перепутать двух людей с одинаковыми именами. `memo` — охранник, который не пускает перерисовку, если на входе (props) ничего не поменялось.

### 3.8 `lazy` + `Suspense` — не грузи то, что пока не нужно

**Где у тебя.** `src/components/pages/AddQuestionPage/AddQuestionPage.lazy.jsx`:

```jsx
export const AddQuestionPageLazy = lazy(() => import("./AddQuestionPage"));
```

И в `src/components/MainLayout/MainLayout.jsx:17-19`:

```jsx
<Suspense fallback={<Loader />}>
  <Outlet />
</Suspense>
```

`lazy(() => import(...))` говорит бандлеру (Vite): не включай код `AddQuestionPage` в основной файл, который грузится сразу при открытии сайта — вынеси его в отдельный файл и подгрузи только тогда, когда пользователь реально перейдёт на `/addquestion`. `Suspense` — это "заглушка на время ожидания": пока отдельный файл ещё не скачался, показываем `<Loader />`.

**Аналогия.** Это как заказ блюда в ресторане только тогда, когда гость его попросил, а не готовить заранее все блюда из меню "на всякий случай".

**Как переносить.** Этот приём стоит применять на страницах/фичах, которые открывают не все пользователи (админка, редко используемые формы, тяжёлые виджеты) — так основной бандл остаётся маленьким.

### 3.9 CSS Modules — стили без конфликтов имён

**Где у тебя.** Практически в каждом компоненте: `import cls from "./Button.module.css"`, дальше `className={cls.btn}`.

Файл с расширением `.module.css` обрабатывается сборщиком по-особому: каждый класс (`.btn`, `.active` и т.д.) на выходе превращается в уникальное имя вроде `Button_btn__a1b2c`. Поэтому если в другом компоненте тоже есть класс `.btn` в своём `.module.css` — они никогда не столкнутся, даже если названы одинаково.

**Аналогия.** Это как если бы у каждого класса CSS была невидимая фамилия, добавленная автоматически — тёзки не путаются.

### 3.10 Barrel-экспорты (`index.jsx`)

**Где у тебя.** Например `src/components/Button/index.jsx`:

```jsx
export {Button} from "./Button"
```

Благодаря этому в других файлах пишешь `import { Button } from "../Button"` вместо `import { Button } from "../Button/Button.jsx"`. Мелочь, но по всему проекту сокращает и унифицирует импорты — папка компонента выглядит как "чёрный ящик" с одной входной дверью.

## 4. Сквозной сценарий целиком: «создание нового вопроса»

Теперь соберём всё вместе на одном полном пути — от клика пользователя до сохранённой карточки. Открой рядом `AddQuestionPage.jsx` и `QuestionForm.jsx`.

1. Пользователь переходит на `/addquestion`. Роутер (3.3) видит совпадение маршрута и рендерит `<AddQuestionPageLazy />`.
2. Так как это `lazy`-компонент (3.8), браузер ещё не скачал его код — на секунду показывается `<Loader />` из `Suspense` в `MainLayout`.
3. Код скачался, `AddQuestionPage` рендерится. Внутри вызывается `useActionState(createCardAction, { clearForm: true })` (3.6) — получаем `formAction` и текущее `formState`.
4. `formState` и `formAction` передаются вниз в переиспользуемый компонент `<QuestionForm />` (3.1) как props.
5. `QuestionForm` рисует `<form action={formAction}>` с полями, у каждого `defaultValue={state.question}` и т.д. — неконтролируемые поля (3.6).
6. Пользователь печатает текст и жмёт кнопку `<Button>{submitBtnText}</Button>` — это компонент из 3.1, у него `type` по умолчанию `submit`, так что клик отправляет форму.
7. React перехватывает отправку формы (никакого `onSubmit` вручную), собирает все значения полей в `FormData` и вызывает `createCardAction(prevState, formData)`. Одновременно `isPending` становится `true`, и `<Loader />` в `AddQuestionPage` появляется на экране.
8. Внутри `createCardAction`: `Object.fromEntries(formData)` превращает данные формы в обычный объект, дальше идёт `fetch(POST)` на `json-server` (по адресу из `API_URL`, 3.2 карта данных).
9. Если сервер ответил ошибкой — попадаем в `catch`, показываем `toast.error(...)` и возвращаем `{}` как новое состояние.
10. Если всё хорошо — `toast.success("Card created successfully")`, и возвращается либо пустой объект (если стоит галочка "очистить форму"), либо только что созданный вопрос — это новое состояние подставится в форму через `state={formState}` при следующем рендере.
11. `isPending` возвращается в `false`, `Loader` исчезает, пользователь видит результат.

Вот так все девять концепций из раздела 3 работают не по отдельности, а вместе, в одном реальном клике пользователя.

## 5. Роадмап: что учить дальше

Это не абстрактный список тем "из интернета" — каждый пункт привязан к твоему собственному коду, чтобы ты учился, **доделывая свой же проект**, а не переключаясь на игрушечные примеры.

### Уровень 0 — прямо сейчас, мини-задания на этом проекте (практика, не теория)

1. **Доделай сохранение в `EditQuestion.jsx`.** Сейчас там `useActionState(() => {}, ...)` — пустой экшен (раздел 3.6). Задание: скопируй структуру `createCardAction` из `AddQuestionPage.jsx`, поменяй `method: "POST"` на `method: "PATCH"` (или `PUT`), URL на `${API_URL}/react/${initialState.id}`, и после успеха сделай `navigate` обратно на страницу вопроса. Это заставит тебя реально понять `useActionState`, а не просто прочитать про него.
2. **Поправь `key={index}` на `key={card.id}`** в `QuestionCardList.jsx` (раздел 3.2) — маленькое, но важное изменение, которое покажет разницу на практике, если добавишь сортировку и последишь за DevTools.
3. **Убери задвоенный запрос карточки.** И `QuestionPage.jsx`, и `EditQuestionPage.jsx` независимо делают `fetch(${API_URL}/react/${id})`. Подумай: можно ли переиспользовать один и тот же код запроса (например, вынести в отдельную функцию в `src/helper` или отдельный хук `useQuestion(id)`)? Это練 практика на тему "когда стоит выносить общую логику".

### Уровень 1 — застолбить фундамент React (следующие 2-3 недели практики)

- **Условный рендеринг и списки** — ты уже используешь, но закрепи: `&&`, тернарный оператор, `.map()` + `key` — прогони через официальный туториал [react.dev — Writing Markup with JSX](https://react.dev/learn/writing-markup-with-jsx) и [Rendering Lists](https://react.dev/learn/rendering-lists).
- **`useState`/`useEffect` глубже** — почему массив зависимостей важен, что такое "stale closure" (устаревшее замыкание), когда эффект должен возвращать функцию очистки (cleanup). У тебя пока нигде нет cleanup-функции в `useEffect` — стоит специально сделать упражнение с `setInterval`/`setTimeout` и очисткой, чтобы прочувствовать, зачем это нужно.
- **Controlled vs uncontrolled формы** — ты видел `defaultValue` (uncontrolled). Специально напиши небольшую форму с `value` + `onChange` (controlled) и сравни на практике: когда нужна валидация "по мере ввода", а когда достаточно uncontrolled.

### Уровень 2 — то, что появляется в реальных проектах и которого пока нет в твоём коде

- **Работа с несколькими похожими запросами и состояние гонки (race condition)** — что будет, если пользователь быстро переключает страницы пагинации, а старый запрос ответит позже нового? Изучи `AbortController` с `fetch`.
- **Формы с валидацией** — сейчас валидация только `required` на уровне HTML. Посмотри в сторону простой ручной валидации или библиотек типа `react-hook-form` / `zod` (когда будешь готов — не обязательно сейчас, сначала пойми ручной способ).
- **Управление состоянием на уровне приложения** — пока весь стейт локальный (в каждой странице свой `useState`). Когда проект вырастет — изучи `useContext` (например, чтобы не тащить `API_URL` и общие данные вручную через props) и, позже, внешние стейт-менеджеры (Zustand, Redux Toolkit) — но не раньше, чем прочувствуешь, зачем они нужны, столкнувшись с "prop drilling" (проброс пропсов через много уровней компонентов).
- **TypeScript** — судя по названию папки проекта (`CourseTSandReact`), это часть твоего плана. Текущий проект написан на чистом JS (`.jsx`, не `.tsx`) — хорошее следующее упражнение: постепенно портировать один-два компонента (начни с `Button`, `Badge` — они самые маленькие) на `.tsx` и описать типы `props`.
- **Тестирование** — в проекте пока нет ни одного теста. Когда дойдёшь до этой темы — начни с простого теста на `QuestionCard` (Vitest + React Testing Library), проверяющего что клик по кнопке вызывает переход по правильному адресу.
